Workspace

forge ships as a 5-crate runtime workspace. Only forge-tui renders to the terminal; the other four layer underneath through strict acyclic dependencies. forge-test-harness is the wire-conformance harness - not in the runtime path.

forge-primitives

Wire-shape types shared across forge-* crates. Message envelopes, content blocks, hook/permission/option/subagent data, render-side views, channel commands, IDs. No logic, no I/O, no async.

depends on: nothing forge-shaped

forge-sdk

Wraps the claude CLI subprocess. Owns the stream-json codec, transport, control dispatch, in-process MCP host, callback registries, and Options builder.

depends on: forge-primitives

forge-agent

Drives one forge-sdk Client behind a channel-based Agent / AgentHandle API. Owns userdata (settings, trust, sessions catalog, memory, plugins), cloud (oauth/usage/account), env (git context), translate, and tooling.

depends on: forge-primitives, forge-sdk

forge-workspace

Multi-session orchestrator and TUI-facing facade. Per-session DomainSession holds operational state; per-session SessionTask actors pump AgentHandle::take_events() into SessionUpdates and route Commands back. The single point of contact between TUI and the agent layer.

depends on: forge-primitives, forge-agent

forge-tui

Native ratatui terminal interface. Pure view layer; consumes SessionUpdate and dispatches Command via forge-workspace. Holds per-session UiSession for presentation state (messages, viewport, input editor, hover hints). The subject of this map.

depends on: forge-primitives, forge-workspace

forge-test-harness

Wire-conformance harness. sdk_wire scope (forge-sdk ↔ claude CLI). Replay-based offline tests + opt-in live capture. Not in the runtime path.

depends on: forge-sdk (transitively gets forge-primitives)

Layout

forge-tui's main frame is a strict vertical stack composed by layout::compute, flanked by inline side panes at the wider tiers. This stack only renders in ActiveView::Chat. When the user opens /config, forge swaps the entire frame to ActiveView::Config - chat / input / side panes all disappear. At terminal widths ≥160 cols the chat frame is flanked by a 40ch Projects pane on the left (carrying the account / mode / model / usage / location panel at its bottom) and a 40ch Inspector pane on the right (carrying the live TASKS list from TodoWrite); between 120-159 cols both panes shrink to 30ch with truncation; below 120 cols a single-row top bar replaces both panes - tapping the ▤ icon (or Ctrl+B) opens the Projects overlay, tapping ▦ (or Ctrl+E) opens the Inspector overlay.

In ActiveView::Chat the central stack is:

  1. body - chat scrollback (Min 3 rows, takes the flex)
  2. input_sep - full-width ─ separator (1 row, DIM)
  3. input - input field (1 row, grows up to N as user types)
  4. input_bottom_sep - full-width ─ separator (1 row, DIM)
  5. help - help overlay (0 when inactive, else HELP_PANEL_HEIGHT = 14)

The mode / model / fast-mode / cwd / branch / usage status used to sit as 2 rows below the input; that row is gone. Mode / Model / Fast / Effort / usage moved to the Projects pane's bottom panel together with the account name and a per-window usage bar (5h, 7d); cwd and branch moved to the right-hand Inspector pane's GIT section (which also surfaces the per-file diff stats). The live todo list used to sit above the input as the todo panel (closed = 1-line compact, open = up to 5 rows, toggle on Ctrl+T); that panel is gone too - todos now render in the Inspector pane as its TASKS section.

Multiple sessions = multiple forge processes, each in its own terminal pane. There is no in-process coordinator view today. Multi-session is the direction we're heading; see the final section.

visible: at all terminal widths - Wide (≥160) renders a 40ch inline pane, Medium (120-159) a 30ch inline pane, Narrow (<120) a single-line top bar with on-demand full-screen overlay

Left-side pane, 40ch wide, docked to the left of the chat frame. Lists projects from forge.toml's [[projects]]. The pane has two anchored regions: the project list grows from the top, and the account / status panel is hard-docked at the bottom. The dim ─ rule between them sits at a fixed row from the bottom - a permanent gutter, not a separator that floats based on list length. The two never overlap. When the project list outgrows its region the list scrolls within itself; the panel never gives up its rows. The empty space above the rule in the mockup above shows what a short project list looks like - the panel still sits at the bottom, gravity is preserved.

The panel's job is to read like account chrome, not "current status." Even though Mode / Model / Ctx flip when the user switches to another session in another project, the panel's shape, position, and labelling stay put. The Profile line at the top of the panel is the anchor - when you switch from your Stargate account's forge session to your Gateway account's data-modules session, Profile flips and Mode / Model / Ctx flip with it, but the panel itself doesn't move. The panel renders, in order:

  • Identity / posture - Profile (active account display name from forge.toml's [[accounts]], via app.active_account_display_name), Org (organization on the active account, sourced from AccountInfo.organization - dim - placeholder until the SDK reports one), ID (first 8 chars of the active session_id with a trailing ⧉ glyph at the right gutter - click the glyph to copy the full session id to the OS clipboard via arboard), Mode (permission mode badge - same colors as the old footer used: auto / acceptEdits yellow, plan blue, bypassPermissions / dontAsk red, default dim), Model (the SDK's display_name_long with any (... context) wrapper folded inline, e.g. Claude Opus 4.7 or Sonnet (200K context) → Sonnet 200K), Effort (always shown on its own row so a long model name can never push it off-screen).
  • Usage bars - three 12-cell filling bars: Ctx (per-session context %), 5h (5-hour plan window), 7d (combined 7-day window). The fill colour is a per-cell position gradient, not a threshold step: cells 1-3 green, 4-6 yellow, 7-9 orange, 10-12 red, so the rightmost filled cell tells you which zone the bar is in. Empty cells stay ░ in DIM. The Ctx bar is followed by a DIM, right-justified token-count on the next line (e.g. 1M / 200K) - the model's raw context-window size from `ContextUsageResponse.raw_max_tokens`. The 5h and 7d rows are followed by a DIM, right-justified duration on the next line (e.g. 1h 48m / 4d 4h) - the legacy resets in prose was dropped so the eye lands on the time, not the verb. A single blank row separates each bar group from the next.
  • Versions - two trailing rows: forge (the running binary's CARGO_PKG_VERSION) and claude (the version reported by claude --version on the local machine). When the npm registry probe finds a strictly-newer published version under the @anthropic-ai/claude-code latest dist-tag, a yellow ↑ vX.Y.Z indicator appends to the claude row. Probes run once at app startup in parallel via Workspace::fetch_cli_version_info; missing values render as - so the row count stays constant.

The 📁 cwd and ⎇ branch rows that used to sit at the bottom of this panel moved to the right-hand Inspector pane's GIT section.

Lead row close: worker cascade

behavior: triggered whenever the lead row's existing x button is clicked on a project that has live workers

The lead row's close button is unchanged in shape: it still dispatches the standard close-session path via PaneHitTarget::CloseSession. The cascade lives inside Workspace::release_session: when the session being released is a lead AND live_workers[project_key] is non-empty, the workspace releases every worker's SessionTask sequentially first, then falls through to the existing lead release path. From the user's perspective this is synchronous: the lead does not return to Sleeping until every worker is gone, which prevents stale Command::DeliverWorkerPrompt dispatches to a freshly-killed lead.

No new Command variant. No new TUI code path. The cascade is observable as a burst of SessionUpdate::WorkerStatusChanged { action: Removed } events (one per worker), followed by the lead's own lifecycle transition. All JSONLs persist on disk; close means "remove from in-memory live state", never "delete from audit trail".

Inspector pane (Wide / Medium / Narrow tiers)

visible: at all terminal widths - Wide (≥160) renders a 40ch inline pane on the right of chat, Medium (120-159) a 30ch inline pane, Narrow (<120) an Inspector ▦ icon on the top bar with on-demand full-screen overlay

Right-side pane, 40ch wide, docked to the right of the chat frame. Mirror of the Projects pane on the left in chrome (banner + rule), Narrow-tier overlay semantics, and persisted-visibility model. The horizontal layout is asymmetric on purpose: the left pane has a │ separator + 1-col padding between it and the chat column; the right pane sits flush against the chat column, using the chat's own scrollbar rail (▕) as the visual divider. The pane's own 2-col content indent provides breathing room from the scrollbar. Reads strictly from the active session - switching projects via the left pane swaps the Inspector's content alongside it.

The banner (INSPECTOR heading + DIM rule beneath it) is pinned at the top - it never scrolls. Everything below it (starting with the GIT section) is a scrollable body: mouse wheel over the body advances the active session's inspector_scroll_offset by 3 lines per notch, and a vertical scrollbar appears on the right edge whenever the body overflows the visible area. The offset lives on UiSession, so switching away to another session and returning preserves where you were looking, same shape as chat scrollback. Same scroll behaviour applies at Narrow tier inside the full-screen overlay.

The pane carries five sections: GIT (always rendered), TASKS (rendered when the focused session has todos or a pending verification nudge), WORKFLOWS (rendered when any Workflow tool call from this session is live or recently completed), SCHEDULES (rendered when any ScheduleWakeup wakeup or CronCreate job is still valid), and PROCESSES (rendered when claude's spawned process tree has at least one descendant alive - foreground / backgrounded Bash, grandchildren like rustc workers). DIM ─ horizontal rules separate adjacent sections so each surface reads visually distinct. The chat scrollback no longer surfaces Task* (formerly TodoWrite) / Workflow / ScheduleWakeup / CronCreate / CronDelete tool-call cards beyond minimal start/end notices; the live state lands transparently in the corresponding Inspector section. Monitor tool calls render their live tail directly in the chat pane (see the Monitor chat surface). Sections render in order: GIT → TASKS → WORKFLOWS → SCHEDULES → PROCESSES; each downstream section is hidden when its content set is empty. PROCESSES is a live monitor sourced from sysinfo's descendant walk - when the last process exits the section disappears. Cron jobs route to the dedicated SCHEDULES section (retired from PROCESSES post-Inspector-SCHEDULES); the prior "Monitor row" kind in PROCESSES is retired and Monitor's live state now renders in the chat pane.

The GIT section shows the focused session's cwd, the current branch on its own line, an optional PR #N → closes #M #K row when the scanner resolved an open pull request, and up to two stacked diff sub-sections - layer 1 (uncommitted: dirty / staged / unstaged tree vs HEAD) and layer 2 (N commits vs <default>: commits ahead of the resolved default branch). Each sub-section carries its own subtitle row + right-justified +A -R totals + box-drawing tree of the top-N changed files grouped by directory. Single-child directory chains fold into one row so paths like crates/forge-agent/src/env/ render as a single header above their file children. The diff side is polled - git_diff shells out to git --numstat every 10 s for the focused session only; a 1 s ticker pokes the drain pump, the rule "snapshot is None OR age ≥ 10 s → fetch" decides whether to spawn a scan. The PR side rides on the same poll but is branch-keyed: the scanner only shells out to gh pr list when the branch name changed since the previous snapshot, so steady-state scans on the same branch reuse the cached PR / closes data for free.

The section follows the focused session, not the lead's. When a worker is selected, the scan runs against the worker's worktree path (<project_root>/.claude/worktrees/<label>/) so the user sees the worker's branch + in-progress edits, not the lead's view of main. The cwd resolution is handled by Workspace::git_scan_cwd_for_session - composing worker_lookup_for_session with the same worker_tag_dir helper that drives the tag-write path.

For a worker on a topic branch with uncommitted edits, both layers populate together - layer 1 shows the in-progress edits, layer 2 shows the committed-but-unmerged work. For the lead on main with a clean tree, neither layer renders and the panel collapses to just the branch row (byte-identical to today's clean-default render). Either layer can render alone when the other is empty.

GIT renders one of these shapes, all keyed off UiSession.git_diff_snapshot:

  • No snapshot yet (pre-first-scan window) - only the path row renders. Branch + layers are added once the first poll completes.
  • Not a git repo (snapshot.repo_gate = RepoGate::NotARepo) - the whole section is suppressed. The user sees no GIT header at all.
  • Clean tree on default branch - path + branch row in DIM. Both worktree and branch_ahead are None, no sub-sections render (or yellow HEAD for detached HEAD + clean tree).
  • Uncommitted edits only - layer 1 sub-section renders below the branch row: uncommitted subtitle + +A -R totals + file tree.
  • Committed but unmerged only - layer 2 sub-section renders: N commits vs <default> subtitle + totals + file tree. Singular form 1 commit vs <default> when only one commit ahead.
  • Both layers - layers 1 and 2 stack, layer 1 first (uncommitted is the more-recent surface). Each carries its own subtitle + tree.
  • Scanner unhealthy (snapshot.repo_gate = RepoGate::ScannerFailed) - DIM-warning line "git scanner unhealthy, see logs (target: agent.env_git)" replaces the layer content, surfacing the failure separately from a legitimate non-repo.

The GIT section header carries a 🦉 glyph at its right edge whenever the snapshot has at least one layer to show. Clicking it opens the full-screen Diff overlay; the auto-detected target prefers layer 1 (HEAD) when both are populated, falling back to the default branch when only layer 2 is set. Hidden when both layers are empty - nothing to expand into. The file trees below the header stay read-only; the only diff entry point on this pane is the header glyph.

The PR #N row is appended directly below the branch row (above any diff layers) whenever the branch has an open pull request resolved by gh pr list --head <branch>. The PR number lights up in RUST_ORANGE (the headline); the PR label, the → separator, the closes label, and the issue numbers all sit in DIM as supporting context. When the closing-issue list would overflow the pane width, fitted issues render in order and the tail collapses to a trailing ... (or to a bare → ... when not even one issue number fits alongside the chrome). Rows are suppressed entirely when there's no open PR, when the branch is the default branch or detached, when gh isn't installed / authenticated, or when the remote isn't a GitHub repository.

When a worker is closed (the x button on its tree-child row, or a cascade triggered by the lead's close), a system-message toast lands in the active session's chat. Git-repo workers read Worker <label> closed. Worktree preserved at .claude/worktrees/<label>/ so the operator knows the worktree survives; non-git workers read the bare Worker <label> closed. form. The toast routes through push_system_message_with_severity(_, Info, _) from the WorkerStatusChanged { Removed } handler.

Item glyphs and styles:

  • ✓ green - Completed (text DIM + crossed-out)
  • ▸ RUST_ORANGE - InProgress (text white bold; uses active_form when present, else content; wraps onto continuation lines indented under the glyph)
  • ○ DIM - Pending (text gray)

Only the in-progress item wraps. Completed and pending items truncate with ... at the pane's right edge - they're scannable status, not actionable text. At Medium tier (30ch) truncation is routine; at Wide tier (40ch) most items fit.

The PROCESSES section surfaces currently-running work in the active session, sitting below SCHEDULES with its own DIM ─ separator. The data source is path A+: the OS process tree under the spawned claude binary is the source of truth for what's alive; wire-tracked tool calls overlay their description when their raw_input.command substring-matches an OS process's cmdline. Two row kinds appear (Monitor was retired from PROCESSES in #273 and now renders in the chat pane; CronCreate was retired in favour of the dedicated SCHEDULES section):

  • Backgrounded Bash - OS process that matched a wire-tracked Bash with run_in_background: true (or claude's CLI auto-promoted foreground Bash). Headline = the assistant's description; detail = the actual OS cmdline.
  • Process - OS process with no matching wire tool call. Foreground Bash invocations, grandchildren (e.g. rustc workers under a cargo build), or anything that's detached from claude's tool registry. Headline = OS process name; detail = OS cmdline.

Where options come from

Options are derived from the CLI's permission_suggestions field (one of the wire fields forge had been ignoring pre-redesign). Three `PermissionUpdate` variants drive the contextual options:

  • addRules (Read outside workspace) → "Allow always for {tool} · paths matching {pattern}". macOS /tmp + /private/tmp mirror entries are deduped for display but both rule entries are kept on the wire so the CLI installs both.
  • addDirectories (Write / Edit outside workspace) → "Allow always & add {dirs} to allowed dirs".
  • setMode (typically arrives on the prompt that intercepts plan-mode - Write outside workspace) → "Allow always & switch to {mode} mode". Note: ExitPlanMode itself sends permission_suggestions: null; the mode switch lives on the earlier intercept prompt, not on ExitPlanMode.

Plus two universally-synthesized options: ... Tell Claude something else (always last) routes to deny(notes_text) on the wire; ✎ Allow with edits (only for editable tools) routes to allow_with_input(edited_value).

Comment workflow

Click on any diff line (added / removed / context - hunk headers are non-interactive) mounts a tui_textarea::TextArea inline below the clicked line. The editor renders with a RUST_ORANGE │ left margin to visually anchor it to the diff; an empty editor shows a DIM "(type your comment, Enter to save, Esc to cancel)" placeholder so first-keystroke shape is obvious. Multi-line edits expand the editor inline; the body keeps scrolling smoothly around it via body_scroll.

  • Enter saves the comment, closes the editor, and renders a bordered mini-box (title 💬 Comment on line <N> + wrapped body rows) in place. Save is idempotent - re-saving on the same anchor replaces the prior entry. Empty saves on a fresh editor are treated as cancel (no chip); empty saves on a reopened chip are treated as delete (matches GitHub's clear-and-save semantics).
  • Esc with an editor open cancels just the editor; the overlay stays. Without an editor open, Esc closes the overlay and (if comments are pending) bundles them into a single markdown user message and dispatches it through the same path a typed prompt takes. The bubble appears in chat immediately + the agent receives the bundle as a fresh prompt.
  • Click on an existing 💬 chip pulls the saved comment back into the editor for re-edit. Saving the edited text puts the chip back in place; cancelling leaves it gone (matches GitHub's edit-or-delete semantics).
  • Switching files via the FILES rail closes any open editor - the editor is anchored to a specific line, and orphaning it on a file switch would confuse the geometry. Saved comments survive file switches; only the in-progress editor drops.
  • Bracketed paste while an editor is open routes to the TextArea so speech-to-text transcripts / clipboard / pasted code blocks all land as expected. Paste outside an open editor is a no-op (nothing for it to land on).
