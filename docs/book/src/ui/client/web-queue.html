What the wire does (measured)

send   forge writes the prompt with uuid 4f9c… - the card enters the pile
queued   {"type":"command_lifecycle","state":"queued","command_uuid":"4f9c…"} - card stays; 1-5 ms after the send
started {"type":"command_lifecycle","state":"started","command_uuid":"4f9c…"} - that card drains into the chat, as the row it becomes, carrying its wait (queued 0:0n · sent); 2-3 ms after the turn boundary. While it waited, the card was the only drawing of the words - the forged chat row is held until this frame
completed {"state":"completed","command_uuid":"4f9c…"} - the turn that carried it ended
delete   {"subtype":"cancel_async_message","message_uuid":"4f9c…"} - the CLI drops it; answers {"cancelled":true}. Too late answers false, and the card has usually drained by then
parked question - every prompt arriving is queued and stays; the answer lands, and all of them go started in the same instant, delivered in the one request that carries the answer
All of this carries only when forge stamps a uuid on each prompt; without it the CLI emits no lifecycle frames at all (measured: 0 frames with no uuid, 6-9 with).
